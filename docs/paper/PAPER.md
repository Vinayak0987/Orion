## Abstract

Producing a business plan requires competence across strategy, finance, branding,
marketing and operations. Large language models can generate plausible prose in all
five areas, but a single generation pass tends to produce internally inconsistent
documents: revenue figures that exceed the market size the same document asserts,
marketing budgets larger than the operating cost base, or workflows assigned to
staff roles that were never hired.

We present MABGP, a multi-agent architecture that decomposes business plan
generation into 21 specialised agents across five departments, coordinated by a
routing orchestrator over a shared append-only state object. Departments execute as
nested directed graphs, with parallelism where agents are independent and explicit
staging where they are not. Two agents are grounded in external data: nearby
competitors are retrieved from a places database and market statistics from web
search, and verified data overrides model-generated data for the same field.

We evaluate the architecture against a single-LLM baseline on four quantitative
metrics — financial accuracy against sector margin benchmarks, competitor coverage
against hand-verified ground truth, plan completeness against a 26-field rubric,
and cross-department consistency — over a fixed set of 35 prompts spanning eight
sectors and four budget scales.

Our findings are mixed and we report them as such. Decomposition markedly improves
completeness and produces internally consistent documents, and dynamic routing
reduces token consumption with no measurable quality loss. However, on financial
accuracy the single-LLM baseline currently outperforms the multi-agent pipeline. We
attribute this to variance compounding: repeating an identical prompt five times per
arm, the multi-agent standard deviation was 4.9× the baseline's, with a 7.6× spread
between best and worst run against the baseline's 1.8×. The pipeline's best run was
more accurate than the baseline's best; it simply does not reliably produce it. We
argue this is a general and under-reported cost of task decomposition, and we
describe the deterministic reconciliation mechanisms that reduced but did not
eliminate it.

**Keywords.** multi-agent systems, large language models, task decomposition,
retrieval grounding, business plan generation, agent orchestration

## 1. Introduction

### 1.1 Motivation

An entrepreneur starting a small business in India needs a plan covering market
positioning, unit economics, brand, customer acquisition and day-to-day operations.
Professional consulting for this costs ₹10,000 to ₹1,00,000 or more. Free templates
provide structure but no analysis, and generic LLM prompting produces text that
reads well but does not hold together under arithmetic scrutiny.

The specific failure we set out to address is *internal inconsistency*. A plan is
not merely a collection of sections; the sections make quantitative claims about the
same business, and those claims must agree. A plan whose Finance section projects
revenue above the market size its own Strategy section calculated is not a partially
correct plan — it is an unusable one, because a reader cannot tell which figure to
believe.

### 1.2 Hypothesis

Assigning each analytical concern to a specialised agent, and forcing all agents to
read from and write to a single shared state object, should produce more complete
and more internally consistent plans than a single generation pass, because:

1. each agent's context contains only what its task requires;
2. an agent that depends on another's output can be made to run after it and read
   its actual result rather than re-deriving it;
3. where two agents assert the same quantity, the disagreement becomes visible and
   can be resolved deterministically.

### 1.3 Research questions

**RQ1.** Does a multi-agent pipeline produce measurably better business plans than a
single-LLM baseline, on financial accuracy, completeness and consistency?

**RQ2.** Does dynamically routing away unnecessary departments improve efficiency
without degrading output quality?

**RQ3.** Does grounding agents in retrieved real-world data improve accuracy
relative to generation from parametric knowledge alone?

### 1.4 Contributions

1. A department-structured multi-agent architecture with an enforced append-only
   state contract, which makes cross-agent disagreement measurable rather than
   masked by last-writer-wins overwrites (§3.3).
2. A deterministic reconciliation mechanism for conflicting quantitative claims
   between agents, and evidence that prompt-level instructions alone are
   insufficient for this (§4.4).
3. A fully quantitative evaluation harness with four metrics, three control arms,
   and an explicit policy of refusing to impute values that cannot be computed
   (§5).
4. A negative result: task decomposition compounds estimation variance, and on
   financial accuracy this outweighs the benefits of specialisation in our system
   (§6.2, §7.2).
5. A reproducible artefact that runs entirely on free-tier infrastructure, with 517
   offline tests and no paid dependency anywhere in the code path (§5.5).

## 2. Related Work

### 2.1 Multi-agent LLM frameworks

**MetaGPT** [1] assigns software-engineering roles to agents and passes structured
documents between them in an assembly-line pattern, showing that role
specialisation plus structured intermediate artefacts outperforms free-form agent
chat. Our department decomposition follows the same principle, with the shared
state object playing the role of MetaGPT's structured documents.

**ChatDev** [2] organises agents into a chat chain for software development and
introduces communicative dehallucination. Where ChatDev reduces hallucination
through dialogue between agents, we reduce it by making certain quantities
non-negotiable: derived arithmetic overrides asserted values (§4.4).

**AutoGen** [3] provides a general framework for conversable, customisable agents
with optional human participation. It is a capability layer rather than an
architecture for a specific task; we use LangGraph for equivalent orchestration
because it exposes the execution graph explicitly, which our routing experiment
(RQ2) manipulates directly.

A recent survey of agentic frameworks [4] compares CrewAI, LangGraph, AutoGen,
Semantic Kernel and MetaGPT on communication, memory and safety. We situate our
orchestration choices against that comparison in §3.2.

### 2.2 Multi-agent systems for business tasks

**BusiAgent** [5] is the closest prior work: a multi-agent LLM framework for
decision-making in corporate environments. It targets established organisations and
managerial decision support. Our scope is narrower and different in kind: generation
of a complete founding plan for a *new* micro or small enterprise from a single
natural-language sentence, with financial projections anchored to a stated budget
and competitors retrieved for a stated locality.

We do not claim novelty in "multi-agent LLM system for business". Our claimed
contributions are the enforced state contract, the deterministic reconciliation of
conflicting agent claims, and the quantitative evaluation against a single-LLM
control — particularly the negative finding on variance compounding, which we have
not seen reported.

### 2.3 Positioning

Most closely related work evaluates on task-completion benchmarks or qualitative
review. We evaluate on metrics external to the system: margins against published
sector benchmarks, and competitors against hand-verified ground truth. This is a
weaker source of ground truth than a unit-test suite affords software-generation
work, and we discuss the consequences in §8.

## 3. System Architecture

### 3.1 Overview

```
natural-language prompt
        ↓
Intent Classifier          hybrid: LLM semantics + deterministic parsing
        ↓
Business Orchestrator      routing rules → active departments → execution DAG
        ↓
Department Layer           5 nested graphs, 21 specialised agents
        ↓
SharedBusinessState        single append-only state object
        ↓
Output Layer               JSON package → HTML report → PDF
```

### 3.2 Orchestration and the execution graph

Routing produces an immutable decision listing active and skipped departments,
which is compiled into a LangGraph `StateGraph`:

```
START ──► strategy ──┬──► finance   ──┐
                     ├──► branding  ──┼──► operations ──► END
                     └──► marketing ──┘
```

Strategy runs first because Finance prices against its competitor set and Marketing
targets its personas. Stage 2's three departments share one superstep and therefore
execute concurrently. Operations has three inbound edges, which makes it a join
barrier: it cannot begin until all of Stage 2 has completed.

For a business with no physical premises, Operations is absent and Stage 2 fans
directly into END. This is the manipulation RQ2 measures, and it is a configuration
flag rather than a code path, so both arms of the experiment run identical code.

Concurrency is verified rather than assumed: a test gives each department runner a
150 ms delay and asserts pairwise overlap of execution windows plus a wall-clock
bound.

### 3.3 Shared state and the append-only contract

All agents read from and write to one `SharedBusinessState` object. An agent may
write only to its own department's section; a cross-department write raises
`StateContractViolation`.

This constraint is what makes the Consistency Score (§5.2) meaningful. If any agent
could overwrite another department's section, a disagreement between two agents
would be silently resolved by whichever wrote last, and the metric would measure
write ordering rather than genuine agreement.

Concurrent writes are handled by two reducer families on the state channels:
telemetry lists concatenate, and department sections merge additively — only
populated fields overwrite, so an agent leaving a field at its default cannot erase
a sibling's output.

### 3.4 Department composition

21 agents, grouped into stages within each department. Same-stage agents run
concurrently; a later stage reads what an earlier stage wrote.

| Department | Stage 1 (parallel) | Stage 2 |
|---|---|---|
| Strategy | market_research · competitive_analysis · location_intelligence | business_planning · risk_analysis |
| Finance | revenue_model · cost_structure | funding_strategy · pl_forecast |
| Branding | brand_naming | brand_identity · brand_voice · visual_design |
| Marketing | buyer_persona | digital_plan · campaign_plan · seo_content |
| Operations | supply_chain · staffing_plan · tech_stack | process_flow |

The staging encodes real dependencies. Business Planning sizes the market against
research that has already run. The P&L agent requires revenue and cost figures. The
three branding agents all reference the name that was selected. Process flow assigns
each workflow step to a role the staffing agent actually created — an assignment that
is checkable, and which we do check (§5.2).

### 3.5 Provider abstraction

No agent imports a vendor SDK. Every call passes through one client that walks a
fallback chain, retries with backoff, and records which provider and model served
the request:

```
STRUCTURED tier  →  Gemini Flash-Lite  →  Groq 8B   →  Ollama (local)
REASONING  tier  →  Groq 70B           →  Gemini    →  Ollama
FAST       tier  →  Groq 8B            →  Gemini    →  Ollama
```

The local terminal link guarantees that a run completes even when both hosted
free tiers are exhausted, which matters for an evaluation sweep issuing hundreds of
calls. The recorded telemetry is what makes the cost and latency figures in §6
reproducible from stored artefacts rather than from re-running the pipeline.

### 3.6 External grounding

Grounding enters through a single hook on the agent base class, so 19 of the 21
agents are unmodified. Two agents override it:

| Agent | Source | Fallback |
|---|---|---|
| competitive_analysis | Google Places → OpenStreetMap | model recall |
| market_research | web search (Serper) | model recall |

Retrieved data overrides generated data for the same field. Each competitor record
retains a `source` label — `google_places`, `openstreetmap` or `llm_inferred` —
which is what allows the two arms of RQ3 to be distinguished in stored output.

## 4. Methodology

### 4.1 Hybrid intent extraction

The classifier splits work between the model and deterministic code:

| Extracted by | Fields |
|---|---|
| LLM | business type, sector, location hints, confidence |
| Regex and gazetteer | budget amount and scale, location normalisation, routing flags |

The split is deliberate and load-bearing for the evaluation. Every financial
projection is anchored to the budget, so if budget parsing varied between providers
the variance in financial accuracy would no longer be attributable to the agents.
Similarly, RQ2 compares dynamic routing against forced all-departments routing on
the same prompts; if the routing decision were itself stochastic the two arms would
not be comparable.

### 4.2 Computed rather than generated arithmetic

The P&L agent is asked for six drivers — opening revenue, exit revenue, COGS
percentage, fixed operating expense, and two growth rates — and all 20 forecast
periods, both margins and the break-even month are then computed in Python.

The reason is measurement validity. Financial accuracy is scored as the error of a
projected margin against a sector benchmark. If the margin were itself generated
text, the metric would partly be scoring the model's arithmetic rather than the
quality of its business assumptions, and it would not be reproducible across
providers.

Cost totals, budget utilisation, payroll and per-channel budget allocations are
derived the same way, from itemised line items rather than asserted totals.

### 4.3 Which margin is compared

Sector benchmarks describe mature businesses. A first-year figure includes start-up
ramp-up and is not comparable to them. Our initial implementation scored the
year-1 average and reported a plausible −9.9% first year as a 182% error against a
+12% benchmark.

We therefore score the *steady-state* margin, taken from the final forecast period.
The year-1 figure is retained and reported separately. Because the single-LLM
baseline reports one margin without distinguishing, the basis used is recorded per
measurement so the comparison can be stated honestly rather than implied to be
identical across arms.

### 4.4 Deterministic reconciliation of conflicting claims

Independent agents produce conflicting estimates of the same quantity. Our first
evaluation sweep exposed five such conflicts, each of which corrupted the financial
accuracy metric:

| Conflict | Observed symptom |
|---|---|
| P&L opex vs cost agent's itemised total | fixed opex below the derived cost base |
| Revenue drivers unbounded | a ₹12 lakh salon projected at ₹9 crore per month by month 12 |
| Revenue ceiling from model-generated market size | obtainable market returned above ₹3 crore for that same salon |
| Year-2 revenue grown from the year-1 *total* | revenue fell entering year 2; steady margin −1% while month 12 was +20% |
| Margin basis mismatch | as §4.3 |

All five are resolved by one rule: **where two agents assert the same quantity, the
derived figure wins over the asserted one.** Cost totals are summed from line items;
P&L operating expense is reconciled against that sum; year-1 revenue is capped at
`min(obtainable market, 10 × stated budget)`.

The budget multiple matters because the obtainable market is itself
model-generated and was observed to be inflated. The cap is arithmetic on a figure
the user supplied, so it holds regardless of what any agent claims.

**A finding worth stating separately:** prompt-level instructions were insufficient.
The market-sizing prompt included an explicit numeric sanity range and the revenue
prompt stated that year-1 revenue must not exceed the obtainable market. Both were
ignored repeatedly. In a multi-agent system, cross-agent constraints must be
enforced in code, not requested in prose.

### 4.5 Lenient output coercion

Small local models emit predictable type errors: nested lists where a flat list of
strings is expected, `null` where a string is expected, and currency-formatted
strings where an integer is expected. Each case was observed on a real run and each
previously cost an agent its entire contribution.

A coercion layer normalises these before validation. It is applied only to agent
output schemas, never to the intent model or the department models, so the frozen
field contract that the metrics depend on retains strict validation.

## 5. Experimental Setup

### 5.1 Arms

| Arm | Manipulation | Serves |
|---|---|---|
| `multi_agent` | full pipeline | treatment |
| `baseline` | one LLM call, same rubric | RQ1 control |
| `all_departments` | routing disabled | RQ2 control |
| `no_grounding` | external retrieval disabled | RQ3 control |

**Baseline fairness.** Three choices deliberately favour the baseline. It receives
the stronger model (`gemini-3.6-flash`) rather than the cheaper one the pipeline uses
for intent extraction. It receives an explicit enumeration of every field the rubric
checks, so it is not penalised for omitting something it was never asked for. It is
scored over all five departments, so its denominator is never smaller than the
treatment's. It also reuses the same deterministic intent classifier, so both arms
agree on budget, location and sector.

The baseline is pinned to one named provider. An earlier implementation allowed the
request to walk the normal fallback chain, and a sweep served the "Gemini baseline"
from a local 3-billion-parameter model — a control that would have invalidated RQ1
silently. A response with fewer than eight populated fields is now recorded as a
failure rather than as a completed plan scoring zero.

### 5.2 Metrics

**F54 Financial Accuracy.** Mean absolute percentage error of the projected
steady-state net margin against the sector benchmark. Margin rather than revenue,
because revenue depends on the scale the entrepreneur chose whereas margin is a
structural property of the sector.

**F55 Competitor Coverage.** Verified competitors found, divided by
hand-collected ground truth within a 2 km radius. Fuzzy name matching accommodates
variants ("Naturals" ≡ "Naturals Ice Cream").

**F56 Plan Completeness.** Expected fields present *and substantive*, over a
26-field rubric. "Substantive" excludes empty lists and short placeholders, which
prevents an arm from scoring well by emitting section headings with no content.
Denominated over active departments only, so correctly skipping a department is not
counted as a quality loss.

**F57 Consistency.** Proportion of applicable cross-department checks that pass.
Nine checks, including revenue within obtainable market, setup cost within budget,
marketing spend within the cost base, net margin below gross, channel shares summing
to 100%, and every workflow owner being a role the staffing plan created.

**F58 Routing Efficiency.** Token and time saving of dynamic routing against the
forced-all control on the same prompt, reported alongside the completeness delta —
a saving is only meaningful if quality holds.

### 5.3 Refusal to impute

A metric that cannot be computed records `applicable=false` with a reason rather
than a zero. Financial accuracy in particular does *not* score a missing margin as
100% error: absence is already penalised by completeness, and counting it twice
would inflate the apparent gap between arms. The generated report lists all unscored
measurements grouped by reason.

### 5.4 Prompt set

35 prompts, held fixed. Eight sectors (food and beverage 6, retail 5, services 5,
education 4, technology 4, healthcare 4, manufacturing 3, creative 4); four budget
scales plus unspecified; eight prompts describing businesses with no physical
premises, which is what gives RQ2 cases where routing can actually skip a
department. Localities are drawn from the classifier's gazetteer so that competitor
lookups resolve.

### 5.5 Reproducibility

All infrastructure is free. Hosted models run on free tiers; the local fallback and
the vector cache require no server. The test suite is 517 tests, runs fully offline,
and a socket guard fails any test that attempts an outbound connection, so the suite
provably consumes no API quota.

```bash
python -m evaluation.harness --all --label paper-run-1
python -m evaluation.report  --label paper-run-1
```

### 5.6 Benchmark provenance

Financial accuracy divides by sector margin benchmarks, so those values determine
the metric. Every benchmark entry carries a source field, unsourced entries are
flagged, and while any benchmark in use is unsourced the generated report labels
the metric PROVISIONAL rather than presenting it as a result.

**This is currently unresolved.** The shipped values are planning midpoints, not
published constants. They must be replaced with cited figures — candidate sources
are the MSME Ministry annual report sector notes, RBI's private corporate business
sector releases, and NSSO unincorporated-enterprise surveys — before §6.2 can be
presented as a finding.

### 6.1 Overall comparison (n ≤ 5, direction only)

| Metric | Direction | multi_agent | baseline |
|---|---|---|---|
| Financial accuracy (MAPE) | lower better | ~132 | **~41** |
| Plan completeness (%) | higher better | **100.0** | 80.8 |
| Consistency (%) | higher better | 97.8 | 100.0 |

### 6.2 RQ1 — multi-agent versus single-LLM

Completeness favours the multi-agent pipeline decisively and consistently: it
reaches 100% of the 26-field rubric where the baseline reaches roughly 81%, and the
baseline's misses are concentrated in the operational detail that a single pass
runs out of attention for.

Consistency is effectively tied. This is a weaker result than we expected, and the
reason is instructive: the baseline emits all five sections in one pass, so it has
little opportunity to contradict itself on the quantities our checks examine. The
consistency metric discriminates between architectures mainly when sections are
produced independently.

**Financial accuracy favours the baseline**, and by a wide margin. §7.2 discusses
why we believe this is a structural property of decomposition rather than an
implementation defect, after five implementation defects had been found and fixed.

### 6.3 Variance under repeated identical input

The same prompt (p01, ice cream shop in Andheri West, ₹15 L) was run five times per
arm. Because the input is identical, all spread is run-to-run variance.

| Arm | n | Mean MAPE | SD | Min | Max | Spread |
|---|---|---|---|---|---|---|
| `baseline` | 3 | 63.1 | 21.2 | 50.0 | 87.5 | 1.8× |
| `multi_agent` | 5 | **158.9** | **103.8** | 38.4 | 290.9 | **7.6×** |

Multi-agent observations: 290.9, 129.1, 239.2, 96.8, 38.4.
Baseline observations: 51.7, 87.5, 50.0.

The multi-agent standard deviation is **4.9× the baseline's**, and its best single
run (38.4) beats the baseline's best (50.0) while its worst is 3.3× the baseline's
worst. The architecture is not reliably worse on financial accuracy; it is
**unreliably better**. This is the evidence for §7.2.

### 6.4 Run reliability

An unplanned observation from the same experiment.

| Arm | Runs | Produced a plan | Completion rate |
|---|---|---|---|
| `multi_agent` | 5 | 5 | **100%** |
| `baseline` | 5 | 3 | 60% |

Both baseline failures were free-tier rate limiting on the pinned provider. The
multi-agent arm completed every run because its provider chain falls through to a
second hosted provider and finally to a local model.

**This comparison must be qualified.** The baseline is pinned to a single named
provider deliberately, so that RQ1 compares against a *stated* model rather than
whatever the chain reaches (§5.1). Its lower reliability is therefore partly an
artefact of that experimental control, not purely an architectural property. The
defensible claim is narrower: a multi-provider fallback chain confers measurable
resilience under free-tier constraints, and the pipeline benefits from it.

### 6.5 RQ2 — dynamic routing

On the prompts where routing actually skipped a department, dynamic routing achieved
a **17.3% token saving with a 0.0 percentage-point completeness delta**. On physical
businesses the two arms route identically and the saving is correctly zero.

RQ2 is supported: efficiency improves and quality does not degrade. This is the
cleanest of our three results, and it is also the least surprising — skipping work
that has no meaningful output saves the tokens that work would have consumed.

### 6.4 RQ3 — grounding

Competitor coverage, the intended headline metric, is **not yet measurable**: it
requires hand-verified ground truth that has not been collected. Reporting a
coverage figure computed against the system's own output would be circular.

The available signal is indirect. Financial accuracy was lower (better) in the
grounded arm than the text-only arm across the smoke run, consistent with grounded
market statistics improving downstream estimates. We regard this as suggestive only.

A separate measured finding concerns provider substitutability. With no billing
account available we used OpenStreetMap in place of Google Places. Live probes in
Bandra, Mumbai found 30 named restaurants and 30 named hairdressers within 2 km, but
zero entries tagged as ice cream shops — Indian ice cream businesses are not tagged
that way. OpenStreetMap also publishes no ratings or review counts at all. It is a
usable substitute for *existence* checking and not for *price positioning*.

## 7. Discussion

### 7.1 What decomposition demonstrably buys

Completeness, and the ability to check internal agreement at all. A 26-field rubric
is reliably filled when 21 agents each own a narrow slice of it. More importantly,
because each agent's contribution is separable and attributable, cross-department
disagreement becomes a measurable quantity. In a single generation pass the same
disagreement exists but is unobservable.

The append-only contract is what makes this true. Without it, the last agent to
write would silently determine the value of any contested field.

### 7.2 What decomposition costs: variance compounding

Our central negative finding. On financial accuracy the single-LLM baseline
outperforms the multi-agent pipeline, and we do not believe this is a defect we
failed to find.

The multi-agent margin is the end of a dependency chain: market sizing produces an
obtainable market, the revenue agent projects against it, the P&L agent derives
drivers from that projection, and margin falls out of the drivers. Each step carries
estimation error, and the errors compose. The baseline emits a margin directly, in
one step, with no chain to accumulate along.

The empirical signature is instability rather than bias. Five runs of the identical
ice-cream prompt produced MAPE of 290.9, 129.1, 239.2, 96.8 and 38.4 — a standard
deviation of 103.8 against the baseline's 21.2 on the same prompt, and a 7.6× spread
between best and worst against the baseline's 1.8× (§6.3).

Two details make this a variance claim rather than an accuracy claim. The
multi-agent arm's *best* run (38.4) beat the baseline's best (50.0), so the pipeline
is capable of the more accurate estimate. And its distribution is far wider, so it
does not reliably produce it. The architecture is unreliably better rather than
reliably worse.

Five implementation defects were found and fixed before we drew this conclusion
(§4.4), reducing MAPE from roughly 180–450 to roughly 70–200. We stopped there
deliberately: further adjustment aimed at the metric would be tuning to the
measurement rather than improving the system.

We suggest this generalises. Any pipeline that decomposes a quantitative estimation
task into dependent stages should expect variance compounding, and should measure it
by repeating identical inputs — a single-shot comparison would have shown only that
the baseline had a better mean, and would have missed the reason. Deterministic
reconciliation at each junction (§4.4) reduces the variance substantially and does
not remove it.

### 7.3 Implications for design

Three practical conclusions.

**Enforce cross-agent constraints in code.** Prompt instructions containing explicit
numeric bounds were ignored repeatedly. Constraints that matter must be
post-conditions, not requests.

**Prefer derived quantities to asserted ones.** Where a value can be computed from
line items the agents already produced, compute it. This resolved every one of our
five conflicts.

**Decompose for coverage, not for numerical precision.** Specialisation reliably
improves breadth and checkability. It did not improve the accuracy of a single
headline number, and made it noisier.

## 8. Limitations

**Sample size.** Results in §6 are from 5 prompts. The 35-prompt sweep is
outstanding, and no claim in §6 should be treated as established until it is run.

**Benchmark provenance.** Financial accuracy divides by unsourced sector margin
estimates (§5.6). The metric is mechanically correct and its absolute values are not
yet defensible. Comparisons *between arms* are less affected, since both arms are
scored against the same benchmark.

**Competitor coverage unmeasured.** RQ3's designated headline metric requires
manual ground truth that has not been collected, so RQ3 rests on indirect evidence.

**Ground truth is weaker than in code generation.** Related work on
software-generating agents can execute unit tests. Business plan quality has no
comparable oracle. Our metrics are proxies, and a plan can satisfy all four while
still being commercially poor.

**Single geography and language.** All prompts are Indian, mostly Mumbai, in
English. The gazetteer, funding schemes, salary bands and sector benchmarks are all
India-specific.

**Model availability drift.** The model named in our original design, Gemini 1.5
Flash, was retired during development and returns 404 for new API keys; Gemini 2.5
Flash is closed to new users. We report the models actually used. This is a
reproducibility hazard for any LLM systems paper and we note it explicitly.

**Free-tier interference.** Burst rate limits caused some agents to fall through to
the local model mid-run, inflating latency from roughly 9 seconds to 24–55 seconds.
Reported timings should be read as free-tier timings, not architectural ones.

**No human evaluation.** We deliberately excluded LLM-as-judge and human rating to
keep every metric reproducible. The cost is that we measure consistency and
completeness but not persuasiveness or practical usefulness.

## 9. Conclusion and Future Work

We built and evaluated a 21-agent architecture for autonomous business plan
generation, and measured it against a single-LLM baseline on four quantitative
metrics with three control arms.

Decomposition improves completeness and makes internal consistency measurable.
Dynamic routing reduces token consumption at no measured quality cost. On financial
accuracy the single-LLM baseline currently wins, which we attribute to variance
compounding along the agent dependency chain, and which we report as a negative
result rather than tune away.

The most transferable outcome is methodological: cross-agent quantitative
constraints must be enforced deterministically in code, because prompt-level
instructions containing explicit numeric bounds were ignored repeatedly by
capable models.

**Future work.** Complete the 35-prompt sweep and source the benchmarks. Collect
competitor ground truth so RQ3 can be answered directly. Investigate variance
reduction by ensembling the estimation chain rather than the individual agents.
Extend beyond a single geography. Add an LLM-as-judge qualitative track alongside
the quantitative metrics, reported separately so the reproducible core stays
reproducible.
