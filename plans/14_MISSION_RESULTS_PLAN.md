# 14 — MISSION RESULTS PLAN (MISSIONS UI)

---

## What It Is and Why It Exists in the System

The Missions section is the **library of everything Orion has ever done**. Every completed mission lives here — findable, reviewable, downloadable, and referenceable.

Plan 03 (Command Center) covers the input side — how a mission starts and streams live. Plan 04 (Mission Engine) covers the backend execution. But neither plan covers what happens **after the mission completes**: how results are displayed, structured, downloaded, and found again.

This plan covers the full Missions UI — the list view, the detail view with its 7 tabs, the output display, and the download/export capability.

**Role in the whole system:** Missions is the permanent record. Command Center is ephemeral (you might close the tab mid-run). Missions persists everything. A user who ran a competitor analysis 2 weeks ago and needs to reference it — Missions is where they go.

## The Two Screens

### Screen 1 — Missions List (`ViewMissions`)

**What it shows:**
- Page header: "Missions" + "New Mission" button (→ navigates to Command Center)
- Tabs: All (12) / Research (4) / Planning (2) / Operations (3) / Completed (2)
- Search bar: filter by mission title/prompt
- Filter dropdowns: Status, Priority, Department, Owner, Date
- Table of missions rows
- Pagination: showing 1-8 of 12, prev/next buttons
- Selected Mission Preview bar at the bottom (shows pipeline of selected mission)

**Each table row shows:**
- Row number
- Mission title (generated from prompt) + description (truncated prompt)
- Type badge: Planning / Research / Operations (classified from task types)
- Agent avatars: stacked circles showing agents that ran
- Progress bar: % of tasks completed
- Status badge: In Progress / Completed / Not Started / Failed
- Last Activity: time ago

**Data source:**
```
GET /missions?limit=50&offset=0&status=&department_id=&search=
```

**Type classification** (derived from task agent_types in mission_tasks):
- Majority research tasks → "Research"
- Contains planning/strategy tasks → "Planning"
- Contains operations tasks → "Operations"
- Mixed → "Planning" (default)

**Clicking a row** → navigates to Mission Details for that mission

**"New Mission" button** → navigates to Command Center

### Screen 2 — Mission Details (`ViewMissionDetails`)

This is the richest screen in the system. It shows everything about one mission.

**Header:**
- Mission icon (generated from type)
- Mission title (from `missions.title` — generated by planner)
- Status badge
- One-line description (truncated prompt)
- Progress ring showing % complete
- "Actions" dropdown: Re-run, Download PDF, Download JSON, Share, Delete

**7 Tabs:**

#### Tab 1: Overview (default)
The execution graph. A live SVG showing:
- Orchestrator node (Orion Planner) at center-left
- Agent nodes in the middle column (one per agent that ran)
- Leaf task nodes on the right (one per task)
- Curved bezier lines connecting them
- Colors: green (completed), blue (in progress), amber (waiting), red (failed)

Source: `GET /missions/{id}` → tasks[] with agent assignments and status

If mission is still running → execution graph updates via polling every 2s.

#### Tab 2: Tasks
Table of all mission tasks:
- Title, assigned agent, status badge, duration, tools used, result summary
- Expandable rows: click to see full task result text

Source: `GET /missions/{id}` → tasks[]

#### Tab 3: Agents
Cards showing each agent that participated:
- Agent name, type, tasks it handled, success rate for this mission
- Link to full agent profile (→ Agents section)

Source: derived from tasks[] + agents DB lookup

#### Tab 4: Tools
List of all tool calls made during this mission:
- Tool name, how many times called, total latency, success rate
- Most expensive tool call highlighted

Source: `GET /missions/{id}/tools` (aggregated from execution_traces for this mission_id)

#### Tab 5: Evidence
All external data the agents gathered:
- Web search results (URLs, snippets)
- Documents retrieved from Knowledge Base
- Maps API results
- Structured as an evidence trail

Source: `GET /missions/{id}/evidence` (tool_output from execution_traces where trace_type=tool)

#### Tab 6: Results
The final outputs of the mission — the main deliverable.

**Structured display:** The mission's outputs organized by task. Each completed task's result shown as a formatted card:
- Task title as heading
- Result text formatted (markdown rendered)
- Key data extracted (numbers, lists, decisions highlighted)

**Download options:**
- Download as HTML Report (formatted, printable)
- Download as PDF (generated server-side)
- Download as JSON (raw structured data)
- Copy to Clipboard

Source: `GET /missions/{id}` → tasks[].result

#### Tab 7: Trace
Technical execution trace (links to Observability):
- Same data as Observability → Trace Details
- Each step: LLM call or tool call, provider, tokens, latency, cost
- "View in Observability" link for full trace

Source: `GET /observability/runs/{mission_id}/trace`

## Download / Export

### HTML Report
```
GET /missions/{id}/report
  generates: formatted HTML document with all task results
  styled with print-friendly CSS
  returns: HTMLResponse
```

### PDF Export
```
GET /missions/{id}/report.pdf
  generates: PDF from the HTML report
  uses: xhtml2pdf (pure Python, works on Windows) or WeasyPrint (Docker)
  returns: Response with Content-Disposition: attachment
  on error: 503 with message "PDF unavailable — use HTML report and print to PDF"
```

### JSON Export
```
GET /missions/{id}/export.json
  returns: { mission_id, prompt, title, status, tasks: [{title, result, agent, tools}], created_at }
```

These endpoints already exist in the current backend (`/sessions/{id}/report`, `/sessions/{id}/report.pdf`). They need to be connected to the new missions table.

## Real-Time Updates (Running Missions)

If a mission is currently running and the user opens Mission Details:
- Status: "In Progress"
- Execution graph: polls `GET /missions/{id}` every 2s to update node states
- Progress ring: updates as tasks complete
- A "Stop Mission" button appears: `DELETE /missions/{id}` → cancels the run

When mission completes:
- Page updates automatically (next poll returns `status: "completed"`)
- Results tab becomes available
- Progress ring = 100%

## Database

No new tables. All data comes from existing tables:
```
missions        → title, status, prompt, created_at, completed_at
mission_tasks   → tasks with agent assignments, status, result
execution_traces → for Tools tab and Trace tab
agents          → for Agents tab (name lookup)
```

## API Endpoints

```
GET  /missions                          list (existing, needs search + type filter)
GET  /missions/{id}                     detail with tasks[] (existing)
GET  /missions/{id}/tools               aggregated tool stats for this mission (NEW)
GET  /missions/{id}/evidence            tool outputs as evidence (NEW)
GET  /missions/{id}/report              HTML report (adapt from existing /sessions/{id}/report)
GET  /missions/{id}/report.pdf          PDF export (adapt from existing)
GET  /missions/{id}/export.json         JSON export (NEW)
DELETE /missions/{id}                   cancel/delete (existing)
```

## How Missions Results Connects to Every Other Plan

| Plan | Connection |
|------|-----------|
| Mission Engine | `GET /missions` and `GET /missions/{id}` read from missions + mission_tasks tables written by Mission Engine |
| Command Center | "New Mission" button → Command Center. Completed missions appear in Command Center chat history. |
| Agents | Agents tab in Mission Details → agents DB lookup for names and links |
| Tools | Tools tab → execution_traces WHERE mission_id = ? AND trace_type = 'tool' |
| Knowledge | Evidence tab → document_rag tool outputs. Results stored in Knowledge for future agent reference. |
| Observability | Trace tab → same data as Observability Trace Details. "View in Observability" link. |
| Operations | Mission results → classified → stored in operations_data (Operations Plan) |
| LLM Provider | Trace tab shows provider/model used per call, latency, cost |
